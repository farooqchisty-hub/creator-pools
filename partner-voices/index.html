Partner Voices

A LinkedIn seeding engine for Brevo Ecom. Build plan, v1.

15 September 2026 · Farooq Chisty · supersedes nothing, first spec

One paragraph. Pay agency owners, ecommerce marketers and DTC founders to post on their own LinkedIn accounts about Brevo Ecom. Reach them by cold email with no figure in it. Get them to quote a rate, counter at half, settle no higher than three quarters, cap everything at $250. Qualify on whether they actually post, not on how many followers they have. Build it by forking the existing outreach-engine repo rather than writing anything new.

2. Base: fork outreach-engine, not the creator engine

farooqchisty-hub/outreach-engine is already the config-driven, forkable extraction of the creator engine: config/campaign.json is the whole customisation surface, src/identity.js is generated from it, templates/ holds every file whose copy can reach a recipient, and scripts/preflight.mjs refuses to deploy a half-rebranded fork. Its motion.kind enum already lists partner_seeding.

Fork that. Do not extend the live creator engine, and do not copy the monolith. Four reasons:

  1. The D1 column ceiling is already reached. creators is 96 columns wide and D1 caps a result set at 100. The pipeline select is already at exactly 100 with joined offer columns, and two offer columns were dropped to make room. This build needs roughly eleven new columns. It does not fit.
  2. The live engine is holding real money and live threads. Adding a second, differently-shaped money policy into negotiation.js puts the creator campaign at risk for no benefit.
  3. Carve-outs are the known bug class. The cloud cutover produced six instances of "a check that was true before the work moved and false after". Conditional gates keyed on creator_kind across the pricing gate, the proof-of-work gate and the evidence rule would manufacture the same class deliberately.
  4. The separation is wanted anyway at the Instantly workspace and sending-domain level, so the split is not artificial.

8. seeding.js, the money policy

One module decides what a counteroffer means. Everything else calls it.

// The three caps. Any one of them can bind.
export const COUNTER_FRACTION     = 0.50;
export const MAX_FRACTION         = 0.75;
export const PROGRAM_CEILING_USD  = 250;
export const ACCEPT_OUTRIGHT_USD  = 150;
export const MAX_PRICED_MESSAGES  = 3;

export function reachCap(medianReactions) {
  // median reactions -> implied impressions -> dollars at the LinkedIn CPM
  return Math.floor((medianReactions * 50 / 1000) * 25);
}

export function maxPayable(quote, medianReactions) {
  return Math.min(
    Math.floor(quote * MAX_FRACTION),
    PROGRAM_CEILING_USD,
    reachCap(medianReactions)
  );
}

export function openingCounter(quote) {
  return Math.floor(quote * COUNTER_FRACTION);
}

export function evaluateSeedingCounter({ quote, theirCounter, medianReactions,
                                         pricedMessages, concessionUsed }) {
  const cap = maxPayable(quote, medianReactions);

  if (quote <= ACCEPT_OUTRIGHT_USD && quote <= PROGRAM_CEILING_USD)
    return { outcome: ACCEPT, fee: quote, why: 'below the haggle threshold' };

  if (openingCounter(quote) > PROGRAM_CEILING_USD)
    return { outcome: ESCALATE, why: 'even our opening counter exceeds the programme ceiling' };

  if (theirCounter == null)
    return { outcome: COUNTER, fee: openingCounter(quote) };

  if (theirCounter <= cap)
    return { outcome: ACCEPT, fee: theirCounter };

  if (concessionUsed || pricedMessages >= MAX_PRICED_MESSAGES)
    return { outcome: WALKAWAY, why: 'above cap, concession spent' };

  // The single move. It is never unconditional.
  return { outcome: COUNTER_CONDITIONAL, fee: cap, requires_trade: true };
}

Three rules the module enforces that are easy to lose:

  • Never improve into silence. A ghost after our counter does not advance pricedMessages and never triggers a better number. Bidding against yourself is the fastest way to lose the ladder.
  • concession_traded_for cannot be null when concession_used = 1. The database refuses it. A free improvement tells them the first number was fake.
  • A quote is captured once. If they revise upward later, that is an escalation, not a new Q. Otherwise the ladder resets and the caps float.

Framing the counter

Budget language, never worth language. "That is above where this campaign's per-post budget sits. I can do $X." The fairness framing that a flat rate would have allowed is unavailable under a quote-relative ladder, because everyone gets a different number and agency owners in this ecosystem talk to each other. Cost, not worth, is the framing that survives them comparing notes.

Cold ladder, no reply

Four touches, in-thread, then stop and nurture for 90 days. Every follow-up must carry new information; "just bumping this" is a deliverability tax.

The reply that asks for a number

Not sent until they answer. It does two things in one message, and the order matters.

  1. Shrink the scope first. One paragraph: one LinkedIn post, their own words and voice, a topic they pick from three, one review round, disclosure included, one payment after it goes live. A rate quoted against "a content collaboration" is a rate-card rate. A rate quoted against a precisely small ask is 30 to 50% lower before any negotiation.
  2. Then ask. "What is your standard rate for a single sponsored post like that?" Standard rate pulls their rate card rather than an opportunistic number. Like that binds it to the scope just described.
  3. Ask for their typical reach on a sponsored post in the same message. It sanity-checks the quote against the data already held, and a refusal is itself information.

Ghosted, two different ladders

Where they went quietCadenceContent rule
After saying yes, before quoting+3d, +8d, then nurture 60dRestate the small scope. No number. Second message closes the loop explicitly

Close conditions

  • Agreed. Move to brief and onboarding.
  • Their floor stays above the cap after the one conditional move.
  • Two follow-ups after their last reply with no response.
  • Explicit no. Thank, suppress, no re-engagement without a new reason.
  • They want a retainer or a package rather than a per-post rate. Different conversation, not this programme's.

Every close is warm and keeps the door open. Bucket 3 are existing partners and bucket 1 are future ones.

A nod is not a reply, and an autoresponder is not a reply at all. On the creator engine, 14 of 18 threads flagged needs_reply were nods, emoji and acknowledgements where silence was correct, and one re-engagement was nearly drafted against a job-application autoresponder. Port the classifier. An out-of-office pauses the ladder until the return date rather than stacking a follow-up on top of it.

13. Bucket 1, played straight

Bucket 1 is in, and it is pitched exactly like the other two. Their Klaviyo tier is their business, not a problem we apologise for in advance. Klaviyo is not mentioned in the opener at all. Naming it hands them a reason to say no before they have heard the offer, and hedging the offer devalues it.

The frame is the offer, and the offer is strong: a selective paid programme, limited slots, and we came to them. An agency owner who reads that as a conflict will say so, and that reply routes to a human. Nobody needs the objection pre-loaded on our behalf.

Operational rules for this bucket:

  • One contact per agency, ever. Inviting three people from one firm on one day reads as a scrape, not as restraint about competitors.
  • Anyone mid-sequence on the existing partner-programme ABM is suppressed until that sequence closes. Two motions on one profile burns both.
  • If they raise the Klaviyo relationship themselves, it escalates to a human. That is routing, not deference.
  • The ask is the post. Not a migration, not a product pitch. They know the category.

One thing that is not negotiable and is not the same thing. The paid disclosure on the published post stays mandatory and still gates the payout. That is FTC, ASA and LinkedIn terms compliance on a piece of published advertising. It has nothing to do with how the offer is pitched, and it is not a hedge.

14. Deliverable, approval and payout

"$100 for every post we approve" is ambiguous in a way that costs money. Define it as a sequence where approval of a draft releases nothing:

  1. Brief. Three topics, they pick one. Versioned in campaign_brief_versions, the version in force recorded on the deliverable.
  2. Draft. They write it in their own voice. We do not supply copy; a supplied post reads as an ad and defeats the entire point.
  3. Review. One round. Factual corrections and the disclosure requirement only, not voice edits.
  4. Post. They publish. They submit the live URL.
  5. Verify. deliverable.js fetches the post and checks three things: it is live, it matches the approved draft, and the disclosure is present. disclosure_verified gates the payout.
  6. Pay. Tolt onboarding link is sent only now, not on first interest. One payment, 3 to 5 business days. Transfer and FX charges are not covered, and that answer is given plainly with no offer of an exception.
  7. Measure. Reactions at 48h and 7d recorded against the fee paid. By month two this gives a real cost per impression and tells you whether $250 is generous or cheap.

Attribution is the gap that makes or breaks the budget case. At $250 a post with no hook, a hundred posts is $25,000 of unmeasurable spend. Every approved post must carry either a UTM'd link or a tagged Brevo mention, and the live URL plus its engagement must be stored. Without that, this programme cannot be defended at renewal.

16. Guards and tests

Every one of these is a defect that has already happened somewhere in this codebase. deploy.sh runs them and refuses to ship on a failure.

  1. A seeding offer can never exceed PROGRAM_CEILING, asserted in the module, at the API and by a database trigger.
  2. PROGRAM_CEILING is declared exactly once. A second literal is not a safety net, it is a second opinion.
  3. A message containing a digit cannot be queued for a creator with no quoted_fee_usd.
  4. The opener contains no currency symbol and no figure, for every bucket.
  5. concession_used = 1 with a null concession_traded_for is rejected.
  6. priced_messages never exceeds 3.
  7. A ghost never increases the offer.
  8. Cold caps read coldSentToday, never channelSentToday.
  9. sendOpener refuses a campaign whose status is not 1.
  10. Inbound polling advances the watermark only when the page set is exhausted.
  11. Sender resolution falls back to LOWER(creators.email) after contact_points.
  12. The drafting MODEL and PRICE_PER_MTOK cannot move independently.
  13. src/schema.js matches the live creators table.
  14. A payout cannot be released with disclosure_verified = 0.
  15. No message can be queued to an address on any protected or internal domain.

17. Ops

  • Cron, 5 minutes, in the Worker. Poll, draft, dispatch, reconcile. Per-tick budgets matched to the interval.
  • Scheduled tasks, ported from the creator engine's five: cycle, monitor, qa, reconcile, sourcing. The .claude/skills/ routines already exist in the fork.
  • Two spend limits fail differently and neither looks like a bug. A Claude Code weekly individual limit kills local scheduled tasks within seconds while the task still reads enabled and lastRunAt keeps advancing. An exhausted Anthropic credit balance kills cloud drafting only, returning a 400 on /api/ops/draft while the cron keeps ticking and reporting success. Monitor both by attempting a real draft, never by checking that a key exists.
  • A bad Pages deploy takes the API down silently. Every /api/* path returns HTTP 200 with the SPA shell and a POST answers 405 from the static handler. Nothing alarms. The monitor must assert on response shape, not status. Recovery: every deployment alias binds the same D1, so the previous deployment is a working API.
  • Deliverable chasing. A separate daily job nudges people who agreed but have not drafted, and people who drafted but have not posted. Different from the outreach ladder and it must not reuse it.
